# Plan: Pre-extract VRM/GLB metadata into asset_files

> **Status:** shipped — migration `034_asset_metadata` adds the bones / materials /
> morph-target / expression JSON columns on `asset_files`. Module doc:
> [`../modules/asset-management.md`](../modules/asset-management.md).

> *(Historical.)* Branch: `claude/dazzling-heisenberg-ri7pj2`
> This plan is the seed context for a cloud worker. It is a starting point, not an
> airtight spec — the worker is interactive and may ask to refine it.

## Goal

Extract a VRM/GLB model's **bones, material names, morph targets (blendshapes), and
expressions** server-side at upload time and store them as JSON on `asset_files`.
The frontend then populates UI lists (bone button + bone rows, material slots,
expression/blendshape dropdowns) from this **persistent, file-keyed metadata**
instead of from live-VRM state produced as a side-effect of the viewport's async
load lifecycle.

### Why

The current per-node store maps (`vrmBonesByNode`, `vrmExpressionsByNode`,
`vrmMorphTargetsByNode`, plus `vrmRegistry` for materials) are derived as a
side-effect of `AvatarNode`'s GLTF-load effect (`Viewport.tsx`) and consumed by
unrelated panels. That couples UI correctness to viewport render state, which has
two confirmed failure modes:

1. **Non-active-scene avatars never populate** — `SceneNodes` only mounts the
   active scene (`rootSceneNodeId === effectiveSceneId`), so an avatar listed in
   another scene's tree has no bones loaded → no bone button.
2. **Model swap goes stale until page reload** — the lists don't refresh
   reliably when a node's `filePath` changes.

Metadata makes the UI a pure, synchronous function of `filePath → metadata`,
eliminating the whole race/coupling class. Scope is **UI population only** — live
manipulation (material editing, expression/pose application) still uses the loaded
VRM and is out of scope.

## Constraints

- **No new runtime deps.** `packages/backend/src/vrm/skeleton.ts` already parses
  GLB (reads the binary, extracts the embedded glTF JSON chunk) for both VRM 0.x
  (`extensions.VRM`) and VRM 1.0 (`extensions.VRMC_vrm`) with zero deps. Reuse
  that approach.
- **Self-heal precedent**: `discoverAssets` in `routes/shared.ts` already
  backfills missing hashes on the asset-list GET. Freshness check follows the
  same shape.
- Metadata extraction must be **non-fatal**: a plain non-VRM `.glb` (no humanoid)
  stores partial/empty metadata, never throws out of the upload/list path.
- Migrations: write the `.sql`; the `.ts` mirror is auto-generated by
  `scripts/buildMigrations.mjs`. Register the migration in `db/index.ts`.
- Do NOT change live rendering / pose / material-apply paths.

## Freshness model

Metadata validity is keyed to the file's content hash (existing `hash` column):
metadata is fresh iff `hash` matches the file's current content. Whenever the hash
is (re)computed, metadata is (re)extracted in the same step, so they can never
disagree.

Cheap gate to avoid sha256-ing every file on every listing: store `file_mtime`
(and reuse existing `size`). In `discoverAssets`, for each row `statSync` the file;
if `size`+`mtime` are unchanged, trust stored hash+metadata. Only on a size/mtime
mismatch recompute sha256; if the hash differs, update `hash`+`size`+`file_mtime`
+`metadata`. This also closes the existing gap where a file overwritten in place
keeps a stale hash (which currently breaks preset re-linking by hash).

## Files in scope

- `packages/backend/src/db/migrations/034_asset_metadata.sql` (new) — add
  `metadata TEXT` and `file_mtime TEXT` (nullable) to `asset_files`.
- `packages/backend/src/db/index.ts` — register migration 034.
- `packages/backend/src/vrm/metadata.ts` (new) — generalize the GLB JSON parse;
  export `extractVrmMetadata(filePath): VrmAssetMetadata` returning
  `{ bones, materials, morphTargets, expressions }`. Reuse/parse the same JSON
  chunk `skeleton.ts` reads (optionally refactor the GLB-JSON read into a shared
  helper both modules use).
- `packages/backend/src/routes/assets.ts` — POST handler: after writing the file,
  if VRM/GLB, extract metadata + record mtime; store on insert.
- `packages/backend/src/routes/shared.ts` — `discoverAssets`: extract metadata on
  newly-discovered files; add the freshness/self-heal loop (size+mtime gate →
  rehash + re-extract).
- `packages/shared/src/types.ts` — extend `AssetFile` with optional
  `metadata: VrmAssetMetadata | null`; add the `VrmAssetMetadata` type.
- `packages/shared/src/schema.ts` — Zod for the metadata shape if assets are
  validated anywhere (check; add if so).
- `packages/frontend/src/api/client.ts` — map the `metadata` column (parse JSON
  string) into the asset DTO.
- `packages/frontend/src/store/editorStore.ts` + `components/editor/SceneGraph.tsx`
  — derive the bone list (first consumer) from asset metadata keyed by the
  avatar node's `filePath`, merging with / falling back to live `vrmBonesByNode`
  when loaded. **Replaces the canonical `VRM_BONE_NAMES` fallback committed in
  `5ab0112`** (was a stopgap for the same gate).

## glТF JSON locations (for the extractor)

- **bones**: `extensions.VRMC_vrm.humanoid.humanBones` (object) / VRM0
  `extensions.VRM.humanoid.humanBones` (array of `{bone,node}`) — already in
  `skeleton.ts`.
- **materials**: top-level `materials[].name`. (MToon flag optional, later.)
- **morphTargets (blendshapes)**: union of `meshes[].primitives[].extras.targetNames`.
- **expressions**: VRM1 `extensions.VRMC_vrm.expressions.preset` keys +
  `.custom` keys; VRM0 `extensions.VRM.blendShapeMaster.blendShapeGroups[].name`.

## Out of scope

- Material editing, expression application, pose application — keep using the live
  VRM. Metadata is read-only UI-population data.
- Hardening the `AvatarNode` live-load store path (lower priority once UI lists no
  longer depend on it).
- Migrating the material-slot and expression/blendshape UIs to metadata — do the
  bone button first as the proof consumer; the others are follow-ups.

## Approach

1. **Backend extraction + storage** (do first, independently shippable):
   migration 034 → `vrm/metadata.ts` → wire into `assets.ts` POST and
   `discoverAssets` (with freshness check) → expose `metadata` in the asset row.
2. **Shared types**: `VrmAssetMetadata` + `AssetFile.metadata`.
3. **Frontend DTO**: parse `metadata` in `client.ts`.
4. **First consumer**: SceneGraph bone button/rows read from asset metadata by
   `filePath`; remove the `VRM_BONE_NAMES` stopgap fallback.
5. (Follow-up) material slots + expression/blendshape dropdowns read from metadata.

## Acceptance / verification

- `pnpm lint` passes.
- Upload a VRM via the API → its `asset_files` row has populated `metadata`
  (bones/materials/morphTargets/expressions).
- Overwrite the file on disk → next asset-list GET refreshes hash + metadata
  (freshness check), confirmed by re-query.
- In the editor: an avatar in a **non-active** scene shows the bone button; after
  switching that node's model, the bone list reflects the new model **without** a
  page reload.
- Non-VRM `.glb` upload does not error; stores empty/partial metadata.
